一、系统概述与设计目标

产品定位：面向个人 / 行政报销场景的桌面工具。输入为电商订单截图（淘宝 / 拼多多 / 美团）与增值税电子发票 PDF，输出为规范化重命名文件 + 可直接导入报销系统的消费明细 Excel。

设计目标：

  • 高准确率的字段抽取：金额 / 平台 / 日期 / 商品名四要素为主，采用「OCR+正则前置 → 大模型兜底」的门控策略，正则能拿准的绝不调模型，兼顾成本与准确率。
  • 零额外依赖的模型接入：大模型后端仅用 Python 标准库 urllib 走 OpenAI 兼容协议，本地（LM Studio / Ollama）与云端（阿里云 MaaS 等）共用同一套代码，无需第三方 SDK。
  • UI 不阻塞：所有重型识别（RapidOCR 推理、HTTP 调用）在 QThread 后台线程执行，GUI 始终可响应。
  • 可分发：PyInstaller onedir 打包，模型权重（ONNX）内置，大模型服务天然外部（HTTP），一键分发无模型负担。
  • 配置驱动的模式路由：5 种识别模式（OCR+正则 / 文字模型·本地 / 文字模型·云端 / 视觉模型·本地 / 视觉模型·云端）由 config.json 与 UI 单选卡驱动，运行时按 model.mode 动态装配后端。

五、数据流说明

5.1 识别主流程（输入 → 解析 → 回填）

  1. 扫描加载：用户选文件夹 → load_folder() 按扩展名（.jpg/.jpeg/.png/.pdf）扫描文件 → 初始化 results=[None]*N、自动定位同目录「订单数据」Excel。
  2. 后台识别（RecognitionWorker.run，逐文件）：
    • PDF → recognize_invoice()（PyMuPDF 结构化解析，不进 OCR/模型管线），输出 {kind:"invoice", amount, date, seller, buyer, invoice_no, product}。
    • 图片 → recognize_image_gated()：
      1. OCR 取文本 → m1_poc.parser.parse() 抽金额/平台 → order_fields 抽日期/商品名。
      2. 门控判定 _need_model()：status≠success，或（商品名空 且 平台≠淘宝）→ 调 model_fn 兜底（文字模型喂 OCR 文本 / 视觉模型喂原图）。
      3. 模型返回以「裁判」为主，正则仅作字段空缺兜底；淘宝商品名故意留空，交后期 Excel 匹配。
  3. 后期处理 _postprocess()（全 Python，不调模型）：
    1. 发票字段归一：platform←seller、order_time←date、product_name←product、invoice_count=1。
    2. 主年份：取本批成功 order_time 中最新年份；0000-MM-DD（模型只读月日/年异常）→ 用主年份补全。
    3. 淘宝匹配：match_by_product()（商品名 LCS 相似度 ≥0.5）→ 失败则 match_by_price()（容差 5 元）兜底；用 Excel 的 订单时间/实付金额/完整商品名 覆盖识别结果。
    4. 四要素复查：图片失败行若四要素补全 → 翻回 success。
  4. 文件名生成：图片成功 → render_template()（或勾选时间前缀时 {date}{platform}{amount}{ext}）；发票 → render_invoice_name() = {日期}-{金额}元-{销售方}-{类别}.pdf。通过 row_done 信号回填表格。

5.2 重命名与导出（结果 → 产物）

  • 执行重命名：execute_rename() 按冲突策略（追加序号）批量重命名，记录 last_renames 支持撤销，写日志。
  • 导出订单汇总：build_order_rows()（时间/商品名/价格/平台/原文件名）→ write_order_excel()。
  • 导出报销导入：build_reimbursement_rows() 仅导出「成功且金额+日期齐全 + 图片商品名齐全」的条目，按模版骨架 write_reimbursement_excel() 生成消费明细（金额/消费日期/发票形式/发票/消费事由）。

七、关键技术决策及其理由

决策方案理由
门控识别（OCR+正则前置 → 模型兜底） 正则能拿准金额/平台/日期就直接用；仅「状态非 success」或「拼多多/美团商品名空」才调大模型 电商截图结构固定，正则准确率与速度远优于模型；大模型仅补缺，显著降低 token 成本与延迟，避免对每张图做昂贵推理
淘宝商品名交后期 Excel 匹配 门控阶段淘宝商品名故意留空，后期用 match_by_product（LCS）/ match_by_price 从订单 Excel 取完整名 视觉模型读出的商品名常过短/有偏差；Excel 中的完整标题更可靠，且能同时补回准确的时间与金额
大模型后端零依赖（stdlib urllib） 自实现 OpenAI 兼容 chat/completions 调用，不引入 requests/openai SDK 本地（LM Studio/Ollama）与云端协议一致；减小打包体积与依赖冲突面；便于 PyInstaller 分发
发票用结构化解析而非 OCR/模型 invoice_parser 用 PyMuPDF 文本 + 词块坐标法定位金额/购销方/税目 电子发票是结构化文本 PDF，正则+坐标法 15 样本验证 100% 吻合；比截图 OCR 更稳、更快、零模型依赖
后台线程（QThread）承载识别 RecognitionWorker 在子线程跑 RapidOCR 加载/推理与 HTTP，信号回传 UI RapidOCR 模型加载重、推理慢；避免阻塞 UI 导致「假死」；单图异常被 try 包裹不影响整体
统一识别结果契约（同构 dict） 图片与发票返回同结构 dict，kind 字段分流；导出归一 platform←seller 等 GUI 表格、重命名、导出共用一套渲染逻辑，消除图片/发票两套分支的维护成本
配置驱动的模式路由 _parse_mode_key / _current_mode 归一 5 种模式；旧标识兼容 运行时按 model.mode 动态装配后端（含 model_fn=None 的纯正则档不加载任何模型），无需改代码即可切换能力
PyInstaller onedir + 外部大模型 exe 内置 ONNX 权重；LM Studio/GGUF 走 localhost HTTP，不入包 启动零解压、分发简单；模型权重更新不影响 exe；目标机单独装 LM Studio 即可换模型
API Key 混淆存储 _obf_encode/_obf_decode 对 config.json 中密钥做轻量混淆 避免明文落盘密钥（非强加密，定位为「防一眼窥视」而非安全边界）
